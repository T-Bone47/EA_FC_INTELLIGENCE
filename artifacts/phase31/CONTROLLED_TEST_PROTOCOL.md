# FC27 matched card comparison

Freeze the card item IDs, build/patch, position and slot, tactical profile, in-game role, outcome metric and direction before the first session. Archive the plan and refer to it with `protocol_key`. Set an anonymized `setup_key` for the same squad, chemistry, opponent or difficulty bracket, and gameplay settings used in both arms. Record platform, mode, controller, skill bracket, and opponent context. Give each match a stable, unique key. Keep player and opponent identifiers out of free text.

Within a session, run the two cards in separate matches at the same slot under the same setup. Keep a common block key, equal recorded playing time, and positions 1 and 2 in the run order. Record the minute total and explicitly observed event counts. Leave unobserved counts null. Record zero only when a count was actually observed. Keep the source locally and identify the report row, page or authorized footage time range through `evidence_locator`. Reviewers compare the reports to the supplied evidence before approving local sharing.

Counterbalance the two run orders across independent sessions. Descriptive rate differences require at least one complete A/B and one complete B/A block in separate reporter/session groups of one protocol and one setup stratum. Exact game patch, formation, slot, position, role, tactic, mode and controller are required for the comparison. Changing platform, skill/opponent context or setup creates a separate stratum. Replayed match keys do not create extra measurements. A disagreement in the source values suppresses that match.

The displayed delta is the first card’s event count per 90 minutes minus the second card’s rate, with a shared denominator from identically timed blocks. This is a descriptive statistic for that outcome, not a claim of total card effectiveness. For example, saves per 90 can rise when a keeper faces more shots. Review that opportunity count separately. The lab reports no interval or winner from the pilot. Related outcomes from one session remain together in later evaluation.

## Intake fields

Submit JSON through **Import structured reports or controlled comparisons**, or POST an array of records to `/api/research/fc27/performance/submissions` under the `records` key with `include_research_data: true`. Use `observation_type: CONTROLLED_EXPERIMENT` and `source_key: controlled`. Each record has the selected `card_item_id`, explicit `rights_attested: true`, optional `share_for_research: true`, `evidence_locator`, a `context` object, and a `match` object. The machine contract is exposed in the application's OpenAPI schema. Regular matches can be entered with the web form and may have different playing time or missing metrics.

For holdout work, register the eligible contexts, outcome direction and performance criteria before seeing results. Freeze independent reporter/setup and chronological session groups as a hash-addressed release. Use only the development part to propose a model change. Evaluate both the current V3.2 baseline and the proposed version on the untouched holdout. Preserve the existing golden test suite. Keep patch or setup changes in separate groups and record why any sessions were excluded.
